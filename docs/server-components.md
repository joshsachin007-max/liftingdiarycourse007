# Server Components

> **ALWAYS first refer to the relevant documentation files within the `/docs` directory before implementation:**
>
> - `/docs/ui.md`
> - `/docs/data-fetching.md`
> - `/docs/auth.md`
> - `/docs/server-components.md`

This app runs **Next.js 16** (App Router). Since Next.js 15, request-time props are **Promises**, and as of Next.js 16 synchronous access is **fully removed** (it was only a temporary compatibility shim in 15). Code that reads `params` or `searchParams` synchronously is a bug.

## 1. `params` and `searchParams` Are Promises (CRITICAL)

In `page.tsx`, `layout.tsx`, `route.ts`, `default.tsx`, and the metadata image files (`opengraph-image`, `twitter-image`, `icon`, `apple-icon`), `params` is a `Promise`. In `page.tsx`, `searchParams` is also a `Promise`.

- Server Component pages and layouts MUST be `async` and MUST `await` the prop before reading from it.
- **NEVER** read `params.workoutId` or `searchParams.date` directly off the prop.
- Type the prop as `Promise<...>`, never as a plain object.

### Correct

```tsx
// src/app/dashboard/workout/[workoutId]/page.tsx
export default async function Page({
  params,
}: {
  params: Promise<{ workoutId: string }>;
}) {
  const { workoutId } = await params;
  // ...
}
```

### Wrong

```tsx
// ❌ Synchronous access — removed in Next.js 16
export default function Page({ params }: { params: { workoutId: string } }) {
  return <p>{params.workoutId}</p>;
}
```

## 2. Prefer the `PageProps` / `LayoutProps` Helpers

Next generates globally available, route-aware types (no import needed). Use them instead of hand-writing the `Promise<...>` shape. Types are generated by `next dev`, `next build`, or `npx next typegen`.

```tsx
// src/app/dashboard/workout/[workoutId]/page.tsx
export default async function Page(props: PageProps<"/dashboard/workout/[workoutId]">) {
  const { workoutId } = await props.params;
  const query = await props.searchParams;
  // ...
}
```

- Use the literal route string so `params` keys are strictly typed and autocomplete works.
- Layouts use `LayoutProps<"/route">` the same way (the root layout already does this with `LayoutProps<"/">`).
- Route handlers use `RouteContext<"/route">`; `await ctx.params` there too.

## 3. Dynamic Route Params in Practice

| Route file                         | URL         | `await params`                |
| ---------------------------------- | ----------- | ----------------------------- |
| `app/shop/[slug]/page.tsx`         | `/shop/1`   | `{ slug: "1" }`               |
| `app/shop/[cat]/[item]/page.tsx`   | `/shop/1/2` | `{ cat: "1", item: "2" }`     |
| `app/shop/[...slug]/page.tsx`      | `/shop/1/2` | `{ slug: ["1", "2"] }`        |

- `searchParams` values are `string | string[] | undefined`; validate/narrow them before use.
- `searchParams` is a plain object (not `URLSearchParams`), and reading it opts the page into **dynamic rendering**.
- Params are **untrusted client input**. Validate them (e.g. with zod) before passing them to a `/src/data` helper, and never use them as a source of `userId` (see `/docs/data-fetching.md`).

### Example with data fetching and auth

```tsx
import { auth } from "@clerk/nextjs/server";
import { notFound, redirect } from "next/navigation";
import { getWorkout } from "@/data/workouts";

export default async function Page(props: PageProps<"/dashboard/workout/[workoutId]">) {
  const { userId } = await auth();
  if (!userId) redirect("/sign-in");

  const { workoutId } = await props.params;

  const workout = await getWorkout(userId, workoutId);
  if (!workout) notFound();

  // ...render, passing data to children as props
}
```

## 4. Other Async Request APIs

These are also async and MUST be awaited: `cookies()`, `headers()`, `draftMode()` (from `next/headers`). Clerk's `auth()` is async too (see `/docs/auth.md`).

```tsx
import { cookies } from "next/headers";

const cookieStore = await cookies();
```

## 5. Client Components Cannot Be `async`

If a Client Component (`"use client"`) page must read `params` / `searchParams`, unwrap the Promise with React's `use()`:

```tsx
"use client";
import { use } from "react";

export default function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = use(params);
  // ...
}
```

Prefer the better pattern: keep the page a Server Component, `await` the params there, and pass plain values to Client Components as props. Do not pass the Promise itself down unless there is a specific reason.

## 6. General Server Component Standards

- Pages and layouts are Server Components by default. Add `"use client"` only for interactivity (state, effects, event handlers, browser APIs), and push it as far down the tree as possible.
- Do all data fetching in Server Components via `/src/data` helpers (see `/docs/data-fetching.md`).
- Do not `await` sequential independent calls — start them together and use `Promise.all`. E.g. `await params` and `await auth()` do not depend on each other.
- Pass only serializable props (no functions, class instances, or Dates that must stay `Date`) from Server to Client Components.
- Use `notFound()` for missing resources and `redirect()` for unauthenticated users; don't render empty shells.

## Migration

If you encounter legacy synchronous access, run the codemod:

```bash
npx @next/codemod@canary next-async-request-api .
```

## Checklist

- [ ] Page/layout is `async` and `await`s `params` / `searchParams` before use
- [ ] Props are typed as `Promise<...>` or via `PageProps` / `LayoutProps`
- [ ] No synchronous `params.x` / `searchParams.x` access anywhere
- [ ] `cookies()`, `headers()`, `draftMode()`, and `auth()` are awaited
- [ ] Params are validated and never used as the source of `userId`
- [ ] `"use client"` components receive plain values, not request Promises
